# `decode_x86_withdecode_extended_operands.l8` vs. a Windows 98 boot

Generated by `x86/tools/l8_expect.py` from the decoded database.
It walks the l8 file's §2 opcode tree and §3 arm list for every
encoding the guest executed, and reports two things: whether an
arm exists,
and whether that arm's `end` is right.

## `end` — the one claim checkable without running the decoder

Each arm's `end` expression is evaluated with `@modrm8` taken from
the real modrm extent and `p.osz`/`p.asz` from the real prefixes,
then compared against the instruction length iced-x86 derived
independently from the same bytes.

| arms exercised | `end` correct | `end` wrong |
|---:|---:|---:|
| 10212 | 10212 | 0 |

**No disagreements.** Every `end` in §3 that Windows 98 exercises is
correct, including the `@modrm8 + p.osz*8` forms where both
terms vary.

## Coverage

| | distinct encodings | executed |
|---|---:|---:|
| reach an arm | 10212 | 388,251,151 |
| fall through to `_` | 5414 | 99,307,538 |

79.6% of executed instructions land on an arm.

The l8 file is a deliberate subset, so a non-empty gap list is
expected; it is the list of arms the file would have to grow to
decode a Windows 98 boot.

### Variants whose arms cover only some addressing modes

These are not subset decisions. The variant HAS arms in §3, but §3
spells them out per modrm kind and the guest uses kinds the file
does not list — `lea` being the clearest case. The enumeration is
over the *same* nine names §1 declares, so the gap is visible by
inspection, which is the property §5.2 claims for arm-local extents.

| variant | arms in §3 | missing modrm kinds |
|---|---|---|
| `lea` | base_d8, base_d32, sib_d32, abs32, reg_direct | `sib_base` (294), `sib_d8` (238), `sib_abs` (102), `base16_d8` (53), `base16_d16` (34), `base` (12), `abs16` (10), `base16` (5) |
