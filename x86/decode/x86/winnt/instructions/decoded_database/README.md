# Decoded instruction database — Windows NT 4.0 boot

Generated by `x86/tools/decode_db.py` from the deduplicated encoding
corpus that an instrumented v86 collects during a live boot
(`x86/decoders/v86/src/rust/l8trace.rs`, feature `l8trace`).

Each row is a **distinct instruction byte string** that Windows NT 4.0
actually executed, decoded into its constituent fields with their
bit offsets, so another decoder can be diffed against it field by
field rather than by mnemonic.

## Files

| file | content |
|---|---|
| `winnt.corpus.jsonl` | raw corpus from the emulator: encoding shape -> up to 2 sample byte strings + execution count |
| `winnt.decoded.jsonl` | one JSON record per distinct byte string, all fields |
| `winnt.decoded.tsv` | the same, flat; the `fields` column is `name@bitoffset:width=value` |
| `winnt.l8_expect.csv` | the l8 test vector: bytes in -> expected `decode(d)` arm, bound arguments and `end` (produced by `x86/tools/l8_expect.py`) |
| `winnt.l8_gaps.md` | which encodings the l8 arm list does not yet cover, and the `end` verdict |

The `.csv` is column-aligned with spaces so it reads as a table; it
is still valid CSV (`csv.reader(f, skipinitialspace=True)`), the
values just need `.strip()`.

## Size

10028 distinct byte strings covering 121,227,593 executed instructions.

`count` belongs to the **encoding shape** (`shape` column), not to
the individual byte string: the emulator counts shapes and keeps up
to two byte strings per shape as displacement/immediate samples, so
two rows sharing a `shape` each report that shape's total and the
figure above double-counts them.  Use `count` as a ranking within a
shape-deduplicated view; for exact dynamic frequencies see the
caveat at the end.

## Validation

Every record is decoded twice — a positional/structural decode
written from the bytes alone, and iced-x86 — and the two are
required to agree on base/index/scale, displacement value and
width, and total length.

| | |
|---|---|
| samples | 12652 |
| ok | 10028 |
| mismatch | 0 |
| page_truncated | 34 |
| undecodable | 0 |

`page_truncated` are samples the emulator cut short at a page
boundary (it will not translate a second page just to trace), not
instructions NT failed to execute.

## Caveat: the JIT path

The corpus is collected on v86's **interpreter** path. v86 only
compiles a block after it has been interpreted enough times to get
hot, so every executed encoding passes through the interpreter at
least once and the *set* of encodings is complete; the `count`
column, however, undercounts hot code by the compiled fraction.
Counts are therefore a ranking, not a census — for exact dynamic
frequencies use `winnt.hist.tsv`, which also instruments the JIT.
