# `decode_x86_withdecode_extended_operands.l8` vs. a Windows NT boot

Generated by `x86/tools/l8_expect.py` from the decoded database.
It walks the l8 file's §2 opcode tree and §3 arm list for every
encoding NT executed, and reports two things: whether an arm exists,
and whether that arm's `end` is right.

## `end` — the one claim checkable without running the decoder

Each arm's `end` expression is evaluated with `@modrm8` taken from
the real modrm extent and `p.osz`/`p.asz` from the real prefixes,
then compared against the instruction length iced-x86 derived
independently from the same bytes.

| arms exercised | `end` correct | `end` wrong |
|---:|---:|---:|
| 6812 | 6812 | 0 |

**No disagreements.** Every `end` in §3 that NT exercises is
correct, including the `@modrm8 + p.osz*8` forms where both
terms vary.

## Coverage

| | distinct encodings | executed |
|---|---:|---:|
| reach an arm | 6812 | 105,717,490 |
| fall through to `_` | 3216 | 15,510,103 |

87.2% of executed instructions land on an arm.

The l8 file is a deliberate subset, so a non-empty gap list is
expected; it is the list of arms the file would have to grow to
decode a Windows NT boot.

### The one that is not a subset decision

`lea` is spelled out per addressing mode in §3 — `base_d8`,
`base_d32`, `sib_d32`, `abs32`, plus `reg_direct` as #UD. NT also
executes `lea` with `sib_base`, `sib_d8`, `sib_abs`, `base`,
`base16_d8`, `base16_d16` and `abs16`. Those arms are missing rather
than omitted: the enumeration is over the *same* nine names §1
declares, so the gap is visible by inspection, which is the
property §5.2 claims for arm-local extents.
